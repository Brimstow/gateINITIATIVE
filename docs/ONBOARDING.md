# gateINITIATIVE Onboarding

`gateinit onboard` is a non-destructive, consent-based onboarding flow that
discovers the agent-instruction files already in your project, asks what you want
to do with each one, previews every filesystem change, and only writes after you
confirm. It is designed to work with ongoing projects — not just green-field ones.

## Why a rewrite?

The original `onboard` command only generated a profile, `.gates.yml`, and some
context rules. It ignored the developer's own agent files (`AGENTS.md`,
`CLAUDE.md`, `.cursorrules`, IDE rules) and could silently overwrite existing
configuration. The new flow treats those files as first-class sources.

## Phases

### 1. Scan

gateINITIATIVE looks for existing instruction files in two scopes:

- **Workspace scope** (files inside your project):
  - Root-level `AGENTS.md`, `CLAUDE.md`, `.cursorrules`, `.windsurfrules`
  - `.github/copilot-instructions.md`
  - Markdown/MDC files under `.cursor/rules`, `.windsurf/rules`, `.claude`
  - User-owned `.rules` / `.voidrules` at the project root (files generated by
    `gateinit bridge` are skipped)
  - Nested `AGENTS.md` / `CLAUDE.md` files up to depth 4 (monorepo support)

- **Global scope** (files outside your project, e.g. `~/.claude/CLAUDE.md`):
  - Scanned and reported, but **never modified**.

For every discovered file gateINITIATIVE reports:

- How many ` ```gate ` / ` ```context ` blocks it contains
- Imperative-sounding prose lines flagged as **candidate rules**
- Whether it is a nested (monorepo) source

### 2. Interview

Interactive mode asks per-source questions:

```text
Apply rules from AGENTS.md? [Y/n]
  Add gateINITIATIVE managed block to AGENTS.md? [y/N]
Include suggestions from global ~/.claude/CLAUDE.md? [Y/n]
Enable test-integrity preset? [Y/n]
Enable security preset? [Y/n]
Enable modular-design preset? [y/N]
Enable paradigm-fit preset? [y/N]
Strictness for presets (strict/standard/advisory) [standard]
```

- Workspace source default: **apply**.
- Global source default: **skip** (report-only).
- Test-integrity and security presets are enabled by default.
- Modular-design and paradigm-fit presets are opt-in.
- `--yes` / non-TTY mode: applies workspace sources, skips global sources, and
  **never injects managed blocks** into instruction files.

### 3. Plan preview

After the interview, gateINITIATIVE prints a Terraform-style write plan:

```text
+ create   .gateinitiative/profile.json
+ create   .gates.yml
+ create   .gateinitiative/context-rules.json
# backup   AGENTS.md
~ modify   AGENTS.md  # idempotent managed block injection
+ create   .gitignore  # ignore .gateinitiative/
```

Symbols:

- `+ create`   — new file
- `~ modify`   — existing file updated (managed block or `.gitignore` append)
- `~ overwrite` — existing file replaced (after backup)
- `# backup`   — copied to `.bak` first
- `- skip`     — no change

`--dry-run` prints this plan and exits without writing anything.

### 4. Execute

After you confirm the plan (or pass `--yes`), gateINITIATIVE performs the actions.
All writes are non-destructive:

- **Existing files are backed up to `.bak`** before being overwritten.
- If `.gates.yml` already exists, generated gates go to `.gates/onboarded.yml`
  instead.
- Re-running `onboard` only replaces context rules that carry
  `generatedBy: 'onboard'`; user-added rules are preserved.
- Managed block injection is **idempotent**: re-running leaves the file
  unchanged (apart from `generatedAt` in the profile).

## Managed block

A managed block is a small static pointer injected into an instruction file you
own:

```markdown
<!-- gateINITIATIVE:begin -->
## gateINITIATIVE Enforcement

This project is enforced by **gateINITIATIVE**. File-level rules ("gates") are actively
enforced by a filesystem daemon — violating writes may be reverted or quarantined.

- Gate definitions: `.gates.yml` (and `.gates/`)
- Recent violations feedback: `.gateinitiative/last-violations.json`
- Validate gates: `gateinit test` · Status: `gateinit status`

Do not edit this block; it is managed by `gateinit onboard`.
<!-- gateINITIATIVE:end -->
```

It is **not** a dump of every gate. It tells the agent where the real rules live.

## Prose candidates

gateINITIATIVE scans instruction files for imperative phrases like
`never`, `always`, `must not`, `do not`, and `don't`. These are listed as
**candidate rules** in the onboarding report but are **never** turned into gates
automatically. If you want one enforced, add it to `.gates.yml` yourself.

## Monorepo support

If an instruction file is found under a subdirectory (e.g.
`packages/api/AGENTS.md`), gateINITIATIVE treats it as scoped to that subtree.
Gates extracted from that file have their trigger globs prefixed with the
subdirectory, so they only fire on files inside `packages/api/`.

## Usage

```bash
# Preview everything, write nothing
bun bin/gateinit.mjs onboard --dry-run

# Non-interactive run (no managed blocks in instruction files)
bun bin/gateinit.mjs onboard --yes

# Interactive run
bun bin/gateinit.mjs onboard

# Use a different project root
bun bin/gateinit.mjs onboard --root ./another-project
```

## Recovery

- `.bak` files are created next to any file gateINITIATIVE backs up.
- `.gates.yml` is never overwritten; generated gates fall back to
  `.gates/onboarded.yml`.
- User-added context rules survive re-runs.
- `--dry-run` lets you inspect every planned change before it happens.

## Related commands

- `gateinit init` — create a starter `.gates.yml`. Refuses if one exists.
- `gateinit test` — run pass/fail fixtures for every loaded gate.
- `gateinit bridge` — generate lean IDE rules from context signals.
- `gateinit review` — approve scoped overrides for blocked files.
- `gateinit clean` — list or delete orphaned external data directories.
